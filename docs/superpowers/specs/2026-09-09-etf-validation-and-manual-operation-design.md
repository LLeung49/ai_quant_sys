# 防御与宽基 ETF：可信验证、归因与每日人工操作单设计

## 1. 目的与边界

本设计把已实现的自适应 `GRID/TREND` 状态机扩展为一条可审计的闭环：历史研究验证、归因可视化、收盘后影子运行、下一交易日人工操作单，以及人工实际成交回填。

使用者依据系统建议自行在券商终端下单。系统**不得**自动下单、撤单、连接交易客户端或导入券商订单 API。任何此类接口均不属于本设计的实现范围。

默认时序固定为：交易日 T 收盘数据完整后计算信号；操作单标记为 T+1 执行；T 日信号不得以 T 日价格成交。若 T+1 非交易日，则使用日历确定的下一交易日。

本期仍只覆盖防御底仓和宽基 Beta 层中的已冻结代表性 ETF/蓝筹标的；债券、贵金属只保留再平衡边界，不纳入 GRID/TREND 有效性结论。

## 2. 当前实现审计结论

已有代码具备可复用基础：

- `engine.py`、`grid.py`、`trend.py`、`execution.py` 已将状态、信号、成交和成本拆开，日间成交与收盘后决策的顺序正确。
- `run_shadow_daily.py` 已是 advice-only 影子运行器，具有冻结选择、数据新鲜度、配置哈希、T+1 建议和禁止券商 API 的导入保护。
- `shadow_store.py` / `mysql_shadow_store.py` 已支持运行、状态、建议和健康检查的持久化；`shadow_report.py` 已能输出中文日报。

但当前滚动验证分支不可信，必须先替换而非在结果上继续调参：

1. 验证窗口缺少独立的指标预热边界，曾导致没有指标/没有成交。
2. 后续的“先跑训练期再截取验证净值”会让训练期成交、现金和持仓进入验证期，构成样本外资金状态污染。
3. 准入逻辑曾以伪造的 `252` 日历史长度通过检查，不能作为正式证据。
4. 当前验证器为加快运行而硬编码默认参数，候选参数选择路径成为死代码；不能宣称完成参数验证。

因此，现有直接诊断只能证明状态机可产生交易，不能用作策略优劣或可实盘结论。

## 3. 统一策略与运行契约

新增一个面向调用方的不可变 `StrategyRunContext`（名称可随现有命名调整），而非复制策略逻辑。它包含：

- 标的、所属层级/子层、策略版本和冻结配置哈希；
- 截止 T 日的完整历史行情、公司行为、交易日历和逐日准入结果；
- 可交易起点、初始现金、初始人工已确认持仓和成本；
- 数据来源、截止日和质量/可成交性状态。

引擎仍只接收既有的 `StrategyState + IndicatorSnapshot + ETFEligibility + AdaptiveConfig` 并产生 `Decision`；研究、影子运行和操作单不得各自实现另一套信号规则。策略输出必须保留：方向、原因枚举、阈值、风险距离、目标预算和数量推导说明。

每一份研究结果和操作单都绑定以下不可变身份：`stock_code`、`as_of_date`、`execution_eligible_date`、`model_version`、`config_hash`、`data_cutoff`。身份不一致即阻断，不得静默继续。

## 4. 可信滚动样本外验证

### 4.1 窗口语义

每个窗口拆成互不混淆的三段：

- 训练段：仅用于从候选集合选择参数；
- 预热段：仅为验证首日计算指标，绝不产生订单、成交、现金或仓位变动；
- 验证段：从零初始资金和零仓位开始计绩效，订单最早于验证段内下一交易日成交。

预热数据可以早于验证首日，但任何预热日的信号均不可排队到验证期。验证基准 B&H 与策略使用相同的开始日、可成交规则、成本口径和资金规模。

正式标的使用既定的 `504/126/126`（训练/验证/步长）滚动窗口；A500 等历史不足者标记为 `reference_only`，使用 `252/126/126`，只展示参考性结果且不能进入激活/冻结候选。

### 4.2 数据与准入

准入计算使用真实、逐日可追溯的历史，而不是以窗口长度填充。任何交易日缺行情、公司行为不完整、日历无法对齐、未确认的复权/原始价格关系，或执行可用性未知时，正式验证失败关闭；报告必须展示失败原因。

请求日期若不是交易日，报告显式记录解析后的起止交易日，不允许静默替换。跨境 ETF 的境内交易日仍按沪深可成交日处理，并对境外标的休市/估值滞后写入数据质量提示。

### 4.3 参数选择和门槛

训练期只从预定义且版本化的候选参数集合中选择；选择依据、全部候选得分和最终参数必须落入窗口产物。正式结果不得以运行速度为由跳过该过程。

ETF 正式通过条件沿用已确认口径：成本后 OOS 年化收益严格高于 B&H；最大回撤最多比 B&H 差 2 个百分点；多数 OOS 窗口不落后。单标的结果只用于判断该标的，层级结论由各自子组合汇总，不能把少数落后标的错误解释为整体失败。

## 5. 归因与可视化产物

每个验证窗口及每个最终汇总生成机器可读 JSON/CSV 与人读 Markdown/PNG（或等价静态图）。最小集合为：

- 价格图：收盘价、实际买卖成交点、未成交/延迟订单、GRID/TREND 切换与止损点；
- 指标图：MA20、布林带、ADX、ATR、MACD（适用时）及每次决策阈值；
- 净值图：策略与成本一致的 B&H 同轴比较，并标记验证起止；
- 归因表：按 `grid_initialize/grid_buy/grid_sell/trend_entry/trend_add/stop/transition/rejected` 统计成交、收益、成本、持仓天数、空仓天数和回撤贡献；
- 可复现清单：窗口边界、原始数据覆盖、参数、配置哈希、运行命令与质量告警。

图的结构参考既有 MACD 样例的“价格+买卖点 / 指标 / 净值”三面板，但数据必须来自引擎事件和净值，不能从图形逻辑反推交易。

## 6. 每日人工操作单

操作单是现有 `run_shadow_daily.py` 的渲染/校验适配层，不替换影子状态机。每天收盘后对已冻结标的生成一张操作单，按以下四种结论之一输出：`买入`、`卖出`、`持有`、`阻断（不建议下单）`。

每条记录必须含：

- 标的代码、名称、层级/子层、资金预算与当前策略仓位；
- 信号日、最早执行日、方向、建议数量/金额、100 份取整规则、参考执行价规则；
- 触发原因、关键阈值、止损/风险线、预估交易成本与数量计算过程；
- 配置哈希、模型版本、数据截止时间/来源、影子运行 ID；
- 人工执行前核对项：真实可用现金、实际可卖份额、交易状态、涨跌停/停牌、价格偏离、单笔与子层预算；
- 阻断或告警的明确原因，以及“需人工确认、系统不会下单”的固定声明。

参考执行价只是开盘前的风险/数量估算，非保证成交价。若人工实际价格使数量、预算或风险距离越界，操作单必须要求重新取整或阻断。人工回填记录实际成交日、价格、份额、费用、未执行原因和确认人；下一次影子运行优先从已回填的真实状态续跑，否则阻断而非假设成交。

## 7. 风控、故障与审计

运行前置检查包括：交易日/收盘截止时间、行情新鲜度、冻结选择存在、配置哈希匹配、状态连续性、账户快照完整性、预算/仓位/可卖份额限制、价格数据质量和公司行为一致性。

任一关键项失败时，只产生带原因的阻断记录，不产生可执行买卖建议。每次生成、人工确认、修改、回填和重跑均以追加式事件审计保存；既有建议不得原地覆盖。

禁止导入 `xtquant`、`xtdata`、broker 或订单 API 的静态保护继续保留，并增加测试覆盖操作单模块。课程项目中可借鉴的是统一策略注册、历史回放、风险检查和健康事件；其自动交易类及其重连/下单方法明确排除。

## 8. 分期与验收

第一期先完成可信验证边界与可视化，重新产出各标的结果；未通过门槛的标的不得进入冻结实盘名单。第二期在已冻结且已验证的标的上接入每日人工操作单与回填。这样不会以未验证策略直接指导真实资金。

验收要求：

1. 测试证明预热期零成交、验证期从独立初始状态开始，且 T 信号只在 T+1 后成交。
2. 测试证明 B&H 与策略的窗口及成本口径一致，准入历史不可伪造。
3. 每份报告能从 JSON/CSV 复算关键指标和图中买卖点。
4. 操作单能在无建议、买卖建议、数据过期、状态不连续、账户/预算不符和人工回填六种情形下正确输出。
5. 静态和集成测试证明每日操作单路径不包含任何自动下单依赖。
