# 原始行情与复权数据采集说明

本文说明 `src/data_ingestion/8-原始行情与复权数据采集.py` 的职责、执行顺序，以及权益事件如何驱动复权价格重刷。

## 1. 这套任务解决什么问题

原有行情任务继续维护旧前复权表 `trade_stock_daily`，不做修改。本任务新增一条独立数据链路，同时保存：

| QMT `dividend_type` | 目标表 | 含义 |
|---|---|---|
| `none` | `trade_stock_daily_raw` | 未复权的原始 OHLC 行情事实 |
| `front` | `trade_stock_daily_qfq` | 独立前复权价格投影 |
| `back` | `trade_stock_daily_bfq` | 独立后复权价格投影 |

此外，它维护权益事件事实表 `trade_corporate_action` 和派生价格刷新任务表 `trade_price_refresh_task`。

旧表和新表并行存在的目的，是先持续对账，再决定是否定向修复旧前复权表。新采集任务**绝不直接写** `trade_stock_daily`。

## 2. 一次日常运行的整体流程

```text
连接 QMT
  ↓
读取三张新价格表的每股票最新日期
  ↓
枚举沪深 A 股与沪深 ETF
  ↓
对每只 A 股：同步最近 10 天权益事件快照，必要时登记重刷任务
  ↓
对每只股票/ETF：下载 none、front、back 三种日线并 UPSERT 到三张新表
  ↓
执行 trade_price_refresh_task 中待处理的历史重刷任务
  ↓
输出行情、权益事件、任务执行、失败股票汇总
```

ETF 跳过权益事件快照，但仍写入三种价格表。A 股与 ETF 都使用三张表中最早的已保存日期作为本轮下载起点；任一模式尚未有数据时，从 `2015-01-01` 开始回补。由于写入是 UPSERT，重叠下载是安全的。

## 3. 普通行情同步

`download_and_save_all_modes()` 按固定顺序调用 `download_and_save_mode()`：

```python
for dividend_type in ("none", "front", "back"):
    download_and_save_mode(stock_code, dividend_type, start_date, adjustment_asof)
```

单个模式的执行步骤：

1. `xtdata.download_history_data()` 确保 QMT 本地日线缓存可用；
2. `xtdata.get_market_data_ex()` 取得指定 `dividend_type` 的 DataFrame；
3. 将 QMT 的 `open/high/low/close/volume/amount` 转为统一行结构；
4. 原始模式额外保存 `preClose`、`suspendFlag`；
5. 调用 `price_projection_store.write_daily_rows()`，按模式写入固定目标表。

QMT 返回空结果不是“当天无行情”的成功情形，而是抛出异常并记录该股票失败，避免错误地把数据缺失吞掉。

`adjustment_asof` 是复权行的数据血缘字段：保存当前股票最新有效权益事件的除权日。它不参与价格计算，用于回答“这一行价格包含到了哪一版权益信息”。

## 4. 权益事件快照：从 QMT 到任务计划

### 4.1 `sync_stock_actions()`

每日对每只 A 股调用一次。它以“今天往前 10 天”为窗口调用：

```python
xtdata.get_divid_factors(stock_code, start_time=..., end_time=...)
```

QMT 返回的 `interest`、`stockBonus`、`stockGift`、`allotNum`、`allotPrice`、`gugai`、`dr` 被规范化为系统字段。原始字段还会保存到 `source_payload`，便于排查供应商字段含义或后续数据修订。

### 4.2 `sync_qmt_factor_snapshot()`

该函数先从 `trade_corporate_action` 查询相同股票、相同来源、相同日期窗口的旧快照，再调用 `plan_factor_snapshot()` 比较新旧事件。

权益事件的比较键是：

```text
(stock_code, ex_date, data_source)
```

只有影响复权的标准化字段变化，才判定为修订。数值统一为固定精度文本/`Decimal`，避免浮点表现差异造成每天重复重刷。

### 4.3 三种变化及其后果

| 情况 | 判断 | 事实表处理 | 前复权任务 | 后复权任务 |
|---|---|---|---|---|
| 新增 | QMT 有、数据库无 | 写入有效事件 | 从 `2015-01-01` 重刷 | 不创建 |
| 修订 | 两边都有，但复权字段不同 | 用 QMT 新值更新 | 从 `2015-01-01` 重刷 | 从除权日重刷 |
| 撤回 | 数据库原有效、QMT 窗口不再返回 | 标记 `cancelled`，不删除 | 从 `2015-01-01` 重刷 | 从除权日重刷 |

前复权以当前价格口径回看历史，因此权益事件改变会影响更早的历史价格，必须从数据起点刷新。后复权正常新增事件可由日常增量下载覆盖；只有历史事件被修订或撤回时，才需要从除权日回补。

### 4.4 `persist_snapshot_plan()` 的事务边界

一个 `SnapshotPlan` 包含：

```text
events_to_upsert  → 新增/修订后的有效权益事件
events_to_cancel  → 需要标记撤回的旧事件
refresh_tasks     → 由这些变化产生的价格重刷请求
```

写入顺序是：

```text
UPSERT 有效权益事件
  ↓
标记撤回权益事件
  ↓
UPSERT 派生价格刷新任务
  ↓
COMMIT
```

三步位于同一个数据库事务。任一步失败时 `ROLLBACK`，因此不会出现“权益事实已更新，但没有创建重刷任务”的半完成状态。

## 5. `trade_price_refresh_task` 如何写入

`_refresh_requests()` 先生成内存中的任务字典，例如：

```python
{
    "stock_code": "600519.SH",
    "price_mode": "front",
    "refresh_from": date(2015, 1, 1),
    "reason": "corporate_action_changed",
}
```

`merge_refresh_tasks()` 会按 `(stock_code, price_mode, reason)` 合并本轮重复任务，保留最早的 `refresh_from`。随后 `persist_snapshot_plan()` 使用 `INSERT_REFRESH_TASK_SQL` 写入 `trade_price_refresh_task`。

数据库 UPSERT 的语义是：

- 同一股票、复权模式、原因的任务重复出现时，取更早的重刷起点；
- 已完成任务再次被权益修订触发时，状态重新变为 `pending`；
- 运行中的旧任务被新任务更新时，也重新变为 `pending`，并清空旧认领令牌；
- 清空历史错误信息，记录新的更新时间。

这意味着任务表保存的是“该股票当前还需要从哪里开始重刷”，而不是每次变化都无限追加一条任务。

## 6. `run_due_refresh_tasks()` 的详细执行逻辑

`main()` 在普通三模式行情增量写入完成后调用：

```python
refresh = run_due_refresh_tasks(refresh_projection)
```

这里的 `refresh_projection` 是一个适配函数。任务执行器只知道任务的三个参数：股票、复权模式、重刷起点；它把这些参数转换为实际 QMT 下载：

```python
download_and_save_mode(
    stock_code,
    price_mode,                 # front 或 back
    refresh_from.strftime("%Y%m%d"),
    get_adjustment_asof(stock_code),
)
```

### 6.1 先回收超时运行任务

执行器首先运行 `RECLAIM_STALE_TASKS_SQL`：

```text
status = running
且 updated_at 早于当前时间 60 分钟
  ↓
改为 failed
retry_count + 1
清空 claim_token
记录“租约已过期，自动回收”
```

典型场景是程序下载历史行情时崩溃或被强制结束。没有这一步，任务会永久停在 `running`，再也不会被选中。

### 6.2 查询可执行任务

随后读取：

```sql
WHERE status IN ('pending', 'failed')
ORDER BY created_at, id
```

- `pending`：新创建，尚未执行；
- `failed`：上次执行失败，需要自动重试；
- `done`：不再执行；
- `running`：正在被其他进程执行，或尚未超过租约。

### 6.3 认领任务，避免并发重复执行

对每条候选任务，执行器生成 UUID：

```python
claim_token = str(uuid4())
```

再执行条件更新：

```sql
UPDATE trade_price_refresh_task
SET status = 'running', claim_token = :token
WHERE id = :id AND status IN ('pending', 'failed')
```

如果更新影响 0 行，说明另一个进程已经先认领，当前进程跳过该任务。

这个 `claim_token` 很重要。例如进程 A 卡住，任务被租约回收并由进程 B 重跑；进程 A 之后恢复时，不能把 B 的新执行状态错误地标记为完成或失败。后续更新都必须同时匹配 `id + running + claim_token`。

### 6.4 实际重刷价格

认领成功后调用：

```python
refresh_price(stock_code, price_mode, refresh_from)
```

在本脚本中，它会重新从 QMT 下载该股票、该复权模式、从 `refresh_from` 至今的全部日线，并 UPSERT 到独立前复权或后复权表。

执行器将以下结果视为失败：

- 回调抛出异常；
- 回调返回 `None` 或 `False`；
- 回调返回数值且小于等于 0。

这样可以防止“QMT 没有返回任何行，但任务被误标完成”。

### 6.5 成功与失败状态转换

成功：

```text
running + 匹配 claim_token
  ↓
done
清空 claim_token、last_error
```

失败：

```text
running + 匹配 claim_token
  ↓
failed
retry_count + 1
保存异常类型和异常消息
清空 claim_token
```

如果状态更新影响 0 行，说明任务在执行期间被新的任务请求覆盖或被其他执行者重新认领；统计为 `superseded`，而不会错误覆盖最新状态。

## 7. 为什么任务在普通增量写入之后执行

顺序是：

```text
先写今天的原始 / 前复权 / 后复权增量行情
  ↓
再执行权益事件驱动的历史重刷
```

这样历史重刷看到的是已包含当天数据的完整时间区间。即使历史重刷与普通增量有日期重叠，也不会产生冲突：两者均为同主键 UPSERT，历史任务最后写入的 QMT 投影即为该权益版本下的最终结果。

## 8. 日常运行与日志阅读

建议顺序：

1. 运行原有前复权采集任务，持续维护旧基准表；
2. 运行本任务，维护原始、独立前复权、后复权、权益事件与刷新任务；
3. 运行 `9-前复权对账与定向重刷.py`，先查看差异；
4. 仅在确认差异后，才使用旧表修复参数。

本任务结尾的三类汇总日志含义：

| 日志前缀 | 含义 |
|---|---|
| `[行情]` | 本轮三种模式写入的行数 |
| `[权益]` | 新增、修订、撤回的权益事件数，以及创建的刷新任务数 |
| `[刷新]` | 历史重刷任务的成功、失败、重试、租约回收、被新任务覆盖数量 |

若存在股票行情失败或刷新任务失败，脚本返回非零退出码，便于 Windows 计划任务或调度器告警。
